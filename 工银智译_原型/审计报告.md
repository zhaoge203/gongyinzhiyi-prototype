## 一、必须尽快修：三个「自查即破」的问题

### 1.1 `interrupt()` 不实声明 —— 最高优先级

**问题**：策划案第四章写「使用 LangGraph 中断机制，实现 human-in-the-loop」，原型 README 同样表述。但代码中：

```
grep interrupt  →  仅出现在文档字符串与注释里
     L13: review_gate 使用 LangGraph 的 interrupt 机制暂停流程...
     L32: from langgraph.checkpoint.memory import MemorySaver
     L207: return g.compile(checkpointer=MemorySaver())
```

`review_gate` 只是一个记录标记并直接连到 `output` 的普通节点，**没有调用 `interrupt()`**，流程不会真正暂停等待人工输入。

**评审风险**：「现场演示一下人工复核怎么停下来？」——演示不了。

**修法**（二选一）：
- A. 真做：在 `review_gate` 调用 `interrupt()`，用 `Command(resume=...)` 恢复，演示暂停/恢复过程。约 30 分钟工作量。
- B. 改口径：改为「预留人工复核闸门，生产阶段接入 LangGraph 中断机制」。

**建议 A**，因为这是策划案「人机协同」卖点的实证，且成本极低。

---

### 1.2 语义保真度指标存在系统性盲区 —— 指标本身不可信

**问题**：`fidelity` 的实现是「解读中的百分比是否在原文任意位置出现过」：

```python
src_pct = extract_percentages(src_text)      # 原文全部百分比
gen_pct = extract_percentages(gen_text)      # 解读全部百分比
unsupported = [p for p in gen_pct if p not in src_pct]
fidelity = (1 - len(unsupported)/len(gen_pct)) * 100
```

只要数值在原文任何地方出现过就通过。**已实测证实该指标 7/7 漏检**：

| 构造的解读 | 保真度 | 应判定 |
|---|---|---|
| 「管理费0.2%，托管费1.2%」（两个数真实，归属对调） | 100.0% | 错误 |
| 「赎回时收您1.5%的赎回费」（1.5% 是申购费） | 100.0% | 错误 |
| 「股票资产占您钱的比例为5%–95%」（实为60%–95%） | 100.0% | 错误 |
| 「审计费用96,000元由您单独支付」（实为基金整体承担） | 100.0% | 错误 |
| 「管理费0.25%，销售服务费0.15%」（对调） | 100.0% | 错误 |
| 「每月运作综合费率0.45%」（实为年化） | 100.0% | 错误 |

复现脚本：`engine/probe_fidelity.py`

**诚实结论**：策划案中「保真度 100%」这个数字在评审眼中若被追问实现方式，会立刻失效。

**修法**：把「数值存在性」升级为「上下文一致性」——
对解读中每个「标签+数值」对，在其绑定的原文锚点块内验证该数值确实挂在同一标签下。
即 `check(fee_plain) = 锚点块内 (标签, 值) 配对一致`。这是可实现的，且能拦住上表全部 6 类错误。

---

### 1.3 交叉校验只查单向 —— 「0 缺陷」是下界而非结论

**问题**：`cross_check` 的逻辑是「正则抽到的值，LLM 必须抽到」：

```python
if b and a and a != b:  diffs.append(...)   # 只有正则有值时才比
if b and not a:         diffs.append(...)
```

当正则为 `None` 时**直接跳过**。因此 LLM 多报一个原文不存在的值时，交叉校验不报警。

**实测副作用**（真实案例）：R1 的「销售服务费 0.25%」，正则因 PDF 表格折行（块内容只剩「务费 0.25% 销售机构」，标签前半被切断）而抽不到，而 LLM 正确还原了完整字段。结果是**校验器对正确答案无记录，对错误答案也无记录**——这个信号目前几乎没有分辨力。

**修法**：交叉校验改为双向——
- 正向：正则有值 → LLM 必须有且一致（现状）
- 反向：LLM 有值 → 必须能在原文锚点块中找到支撑（新增，可复用 1.2 的上下文一致性检查）

## 二、需要讨论：四个方向性判断

### 2.1 真实用户理解度 = 零证据

策划案的核心承诺是「让投资者真正读懂」。但全部指标都是**代理指标**：平均句长、术语密度、锚点有效率。

而这些代理指标与「读懂」之间是**假设关系，不是已证关系**。更麻烦的是：我在 chain3 里加了「长句机械拆分」后处理（在标点处断句），这会让平均句长指标变好看，但**拆分本身可能降低可读性**——把「因为 A，所以 B」拆成「因为 A。所以 B。」反而更难读。

一审：R3 解读平均句长 12.5 字，已接近机械拆分的产物特征。

**讨论点**：是否要在策划案中明确「理解度验证」为下一阶段目标，并给出具体的实验设计（如 20-30 人对照实验：读原文组 vs 读解读组，做同一套理解题）？

这会把「我们相信它更好读」变成「我们计划如何证明它更好读」。评审对后者的接受度远高于前者。

---

### 2.2 「不推荐」与「并列对照」之间的边界

策划案反复强调「不评分、不排序、不推荐」，但界面稿 `ui_3_comparison.png` 把高费率标红、低费率标绿，且「3.52 倍」加粗突出。

**讨论点**：这算不算构成事实上的推荐？监管口径下，「同口径并列披露 + 差值提示」与「暗示某产品更优」的界线在哪里？

可能的稳妥做法：去掉红绿色彩编码，只做中性并列；差值作为纯事实陈述放在表下注脚，不做视觉强调。

---

### 2.3 品类口径：基金 vs 银行理财产品

原型证明的是**基金产品资料概要**。但「工银智译」这个名字与「财富管理服务」赛道都指向银行系财富管理，而基金代销只是其中一环。

**需要核实的关键事实**（我尚未查证）：内地的**银行理财产品**是否有等同的「资料概要」强制性定期披露文件？如果只有基金有 KFS 而理财产品没有，那么「同一套能力覆盖两类文件」这个论断就站不住，扩展路径需要重写。

**讨论点**：是先查清这一点再定扩展叙事，还是把首发品类就锁定为基金、把理财产品写成长期方向？

---

### 2.4 认知确认题不存在

策划案三个应用场景都写了「推送认知确认题，答错触发人工说明」，第四章还说这是「适当性管理最后一公里」。**原型里没有任何一道确认题**——`chain3` 不生成题目，也没有答题逻辑。

这是策划案中最容易被现场追问的功能（因为它最贴近监管痛点），却是完全空缺的。

**修法**：用已有的风险条目自动生成 3 道选择题（成本很低，且能顺带做「理解度」验证的载体）。

## 三、量级与稳健性

### 3.1 样本量 4 份 —— 得说清是演示还是验证

4 份文件覆盖了完整风险梯度（这是优点），但作为「验证」样本量太小。**且 4 份全部来自同一家管理人（工银瑞信）的同一模板**——同一模板意味着解析难度被系统性低估。

**建议**：策划案中把「4 份」定位为「可行性验证」，明确说明「跨管理人、跨文件的稳健性验证为下一阶段工作」，并给出目标样本量（如 100+ 只、覆盖 ≥5 家管理人）。

### 3.2 成本与规模完全未测算

策划案说「边际成本极低」，但没有任何数字：单次解读的 token 成本、全量产品月更新的成本量级、算力投入。

**评审风险**：「工行有上万只代销产品，每月都更新概要，这套系统跑一遍要多少钱？」

**建议**：补一个粗略但结构正确的测算（单份文件字数 → token 量 → 单次成本 → 月度全量成本），哪怕给区间也比没有好。

### 3.3 文档版本与解读版本未挂接

产品资料概要「信息发生重大变更的三个工作日内更新，其他信息每年更新一次」。**更新频繁，且多数更新只是数据刷新而非文本变化**。

当前设计没有版本管理：如果每次更新都重新生成解读，会出现
- 同一产品解读文案反复变动（投资者困惑）
- 无意义的重复成本
- 无法回答「这份解读对应哪一版文件」

**建议**：增加「文档版本 → 解读版本」绑定 + 变更检测（文本未变则复用既有解读）。这既是成本优化，也是可审计性的必要组成。

## 六、诚实评价

**做得实的部分**：
- 原型真实跑通，四份真实文档全流程无人工干预通过
- 四个实测问题（PDF 表格压平、合规红线误拦「不保本」、结构化输出失败回退、句长反增被门禁拦下）都是真实的、有日志的工程发现，这类内容比漂亮指标更能取信
- 同类产品对照（3.52 倍费率差、同为「开放式」却锁定 3 年）是有实质价值的发现，且直接来自真实数据

**做得虚的部分**：
- 所有质量指标都是下界或代理，「100%」的说服力被高估
- 用户价值主张（更好理解）零实证
- 规模、成本、稳健性均未触及
- 有一处技术声明（interrupt）不实

**核心判断**：产品的技术骨架是扎实的，问题集中在**"我们如何证明它有用"**这一环。当前的指标体系看起来完整，实则是「防错」体系（确保没讲错），而不是「有效性」体系（证明讲明白了）。前者是必要条件，后者才是这个项目存在的理由。
